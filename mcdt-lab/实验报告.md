## 1 Lab1：把三个测试用例实现出来

### 1.1 先回答实验文档里的问题：`gen_stop_callback()` 和 `run_stop_callback()` 干什么

`mcdt_root_test::run()` 里的线程结构是这样的：

```
fork
  agents[0..2].run()    // driver + monitor
  mcdt_mon.run()
  chker.run()
join_none                        ← 环境先跑起来
fork
  gen_stop_callback();           ← ① "什么时候该停止激励"
  @(gen_stop_e) disable gen_threads;
join_none
fork : gen_threads
  gen[0..2].run()                ← ② 三个generator并行发包
join
run_stop_callback();             ← ③ "激励停了以后还要等什么、什么时候结束仿真"
```

- **`gen_stop_callback()` 管“停止激励的条件”**。默认是空任务，也就是让三个
  generator 自己把 `ntrans` 个包发完。因为它和 `@(gen_stop_e) disable gen_threads`
  一起 fork，所以子类只要在条件满足时 `-> gen_stop_e`，就能把还在 `repeat(ntrans)`
  里跑的三个 generator 线程整体掐掉——这是“激励端提前收手”的开关。
- **`run_stop_callback()` 管“收尾和结束”**。默认实现是 `run_stop_flags.get(3)`，
  等三个 generator 各自发完包后往信号量里放一个 key（`run_stop_flags.put()`），
  凑满 3 个才 `$finish()`。它的语义是“环境不能比激励先死”——否则最后几个包还在
  DUT 的 FIFO 里没搬出来，checker 就少比了数据。

这两个回调的存在，使得**同一个 `run()` 流程可以派生出三种完全不同的“停止策略”**：
basic/burst 是“发完就停”，fifo_full 是“外部条件满足就掐断、再等 DUT 排空”。

### 1.2 `mcdt_burst_test`（TODO-1）

要求：每个通道发包数在 `[80:100]`，`data_nidles==0`、`pkt_nidles==1`、
`data_size inside {8,16,32}`。

```systemverilog
foreach(gen[i]) begin
  assert(gen[i].randomize() with {ch_id == local::i;
                                  ntrans inside {[80:100]};
                                  data_nidles == 0;
                                  pkt_nidles == 1;
                                  data_size inside {8, 16, 32};
                                 })
    else $fatal("[RNDFAIL] gen[%0d] randomization failure!", i);
end
```

两个细节：

- `data_nidles==0` 表示包内数据之间不留空拍，`pkt_nidles==1` 表示包间只留 1 拍，
  两者合起来才是“连续多拍突发 + 相邻包背靠背”。所以波形上应该看到
  `ch_valid` 连续拉高 N 拍、拉低 1 拍、再连续拉高。
- 我给每个 generator 加了 `ch_id == local::i`。原因是 `chnl_trans` 里数据内容是
  按 `'hC000_0000 + (ch_id<<24) + (pkt_id<<8) + i` 编码的，如果三个通道都用默认
  `ch_id=0`，三路数据就完全一样，波形上根本分不出是谁的。加上通道号之后，
  数据高字节就是通道标签：`C0xxxxxx` = ch0、`C1xxxxxx` = ch1、`C2xxxxxx` = ch2。

### 1.3 `mcdt_fifo_full_test`（TODO-2）

要求：保持通道持续发包，让**至少两个** slave 通道同时 `ready==0`（FIFO 满），
并且在 channel FIFO 里的数据全部送出去之后才停。

三个部分分别填在 `do_config()` / `gen_stop_callback()` / `run_stop_callback()`：

```systemverilog
// do_config：把包数开到很大，保证"FIFO写满之前generator不会先跑完"
assert(gen[i].randomize() with {ch_id == local::i;
                                ntrans inside {[1000:2000]};
                                data_nidles == 0; pkt_nidles == 1;
                                data_size inside {8, 16, 32};})

// gen_stop_callback：ready为高的通道数<=1 就等价于"至少2个通道ready为低"
@(posedge agents[0].vif.rstn);
forever begin
  @(posedge agents[0].vif.clk);
  chnl_ready_flags = this.get_chnl_ready_flags();
  if($countones(chnl_ready_flags) <= 1) break;
end
-> this.gen_stop_e;                    // 掐断gen_threads

// run_stop_callback：不能再等run_stop_flags(被掐断的generator不会put)，
// 改成等三个FIFO的margin都回到32(6'h20)，也就是DUT把残留数据搬空
fork
  wait(agents[0].vif.ch_margin == 'h20);
  wait(agents[1].vif.ch_margin == 'h20);
  wait(agents[2].vif.ch_margin == 'h20);
join
$finish();
```

这里的“至少两个通道满”为什么一定会发生：三个通道都以 1 拍 1 个数据的速率写入，
而 arbiter 每拍只能搬走 1 个数据，净增长是 +2/拍，三个 32 深的 FIFO 迟早会被写满。
实测停止时 `ready flags = 'b100`（ch0、ch1 已经满，只有 ch2 还 ready）。

### 1.4 在波形里检查 BURST

`make run TESTNAME=mcdt_burst_test` 会额外存一份 `mcdt_burst_test.wlf`，
用 `vsim -view mcdt_burst_test.wlf` 打开即可。看三处：

1. `chnl0_if.ch_valid / ch_data`：`ch_valid` 应该是“长连续高、中间只断 1 拍”的规律，
   数据在包内连续递增（`...00, 01, 02, ...`）；
2. `chnlX_if.ch_ready / ch_margin`：`ch_margin` 是 FIFO 可写余量（32=空、0=满），
   突发期间会看到它一路掉到 0，然后 `ch_ready` 拉低把 driver 卡住（这就是 FIFO 满的握手行为）；
3. `mcdt_if.mcdt_val / mcdt_id / mcdt_data`：输出侧每拍一个数据，`mcdt_id` 在轮询地
   0→1→2→0 跳变，说明 arbiter 在公平地轮转。

## 2 Lab2：把覆盖率做到验收要求

### 2.1 覆盖率采集流程

按实验文档的意图，**覆盖率编译选项只加在设计文件上**（TB 和 package 不加，
否则会把验证平台的代码也算进分母），所以 `comp` 分两次编译：

```makefile
VCOMP_D = vlog -work ./work -cover bst -sv ... $(DFILES)    # 只给RTL加 -cover bst
VCOMP_V = vlog -work ./work -sv ...       $(VFILES)         # TB/package 不加
```

`bst` = branch + statement + toggle，正好对应文档里要勾的 Branches / Statements / Toggles。
仿真侧：

```makefile
vsim -c -voptargs=+acc -work ./work tb -coverage -assertdebug -assertcounts \
     -classdebug -solvefaildebug -sv_seed $SEED +TESTNAME=$TESTNAME \
     -do "coverage save -onexit cov/runs/${TESTNAME}_${SEED}.ucdb; run -all; quit -f"
```

用 `coverage save -onexit` 落一个以“用例名_种子”命名的 UCDB，效果和文档里的
`-coverage -coverstore <path> -testname <name>` 一样（都会在退出时按 test 名归档），
但文件名更直观、合并时不用猜。最后：

```bash
vcover merge -out cov/merged.ucdb cov/runs/*.ucdb
vcover report -html -output cov/html -details cov/merged.ucdb
```

注：QuestaSim 2021.1 里没有 `-assertcover` 这个开关（文档里的写法应该是老版本或者笔误），
断言覆盖率用 `-assertdebug -assertcounts` 就够了。

### 2.2 第一轮：只跑 `basic_test`，看漏洞在哪

第一轮只跑 `mcdt_basic_test` 一个用例时，问题很典型：

- **代码覆盖率**：`slave_fifo` 的 statement/branch 都满，但 **toggle 只有 62%**。
  明细看下去，缺的是 `chx_data_i[5-7]`、`chx_data_i[16-29]`、`slvx_data_o[16-31]`
  这些位——因为它们永远是常数。
- **功能覆盖率**：`cg_fifo_state.fifos` 的 `all_fifo_full`、`cg_arbiter_data.id` 的
  `diff[1=>0]`、`cg_arbitration.req2[3]`、以及 `validXid` 里三个 `*_single` 都是 0。
- **断言/覆盖点**：3 个 `cover property` 里 `p_read_only`（只有读没有写）没命中。

原因是 `basic_test` 只有一个数据画像：包长大、包间有 3~10 拍空隙、数据内容带固定高字节。

### 2.3 针对漏洞补的 4 个用例

| 新用例 | 参数 | 补哪个洞 |
|--------|------|---------|
| `mcdt_single_test` | `data_size==1`、`pkt_nidles 6~10` | `cg_channel_data.chnlX.single` 的 (0=>1=>0)；`cg_arbiter_data.valid.single`；`p_read_only` |
| `mcdt_alone_test` | `+CHID=0/1/2`，主角通道发 200 包、其余只发 3 包 | `cg_arbiter_data.id.same` 的 (0=>0)/(1=>1)/(2=>2)：只剩一路请求时轮询状态机停在同态 |
| `mcdt_pair_test` | `+CHPAIR=0/1/2`，只让两个通道活跃 | `cg_arbitration.req2` 的三个“两路请求”bin；`cg_arbiter_data.id.diff` 的对角转移，例如 (1=>0) 只在“ch0、ch1 有请求而 ch2 没有”时出现（GRANT1 → GRANT0） |
| `mcdt_random_test` | 关闭数据编码约束，用 32 位全随机数据 | **toggle**：常量高位（bit31:26、bit23:16、bit7:5）只有吃到随机数据才会翻转 |

前三个都是“改约束/加场景”，第四个是“改数据内容”，文档里也明确说了
“当最终覆盖率无法提升时，需要修改你的约束，或者创建新的 test”。

`mcdt_random_test` 的做法是在 `chnl_trans` 里加一个静态开关，把
“数据内容 = 通道标签编码”这条约束变成可关的：

```systemverilog
static bit random_data_en = 0;      // 0=数据带通道标签，1=全随机
constraint cstr{
  soft data.size inside {[4:8]};
  if(!random_data_en) foreach(data[i]) data[i] == 'hC000_0000 + (this.ch_id<<24) + (this.pkt_id<<8) + i;
  ...
};
```

DUT 对数据内容是透明的（数据不参与任何逻辑判断，只从 FIFO 搬到输出口），
所以换随机数据不影响功能检查，checker 依然是逐拍逐通道比对。

### 2.3.1 补用例时踩到的一个坑：约束区间越界

`mcdt_single_test` 最初把 `pkt_nidles` 写成 `inside {[6:12]}`，跑种子 1 没问题，
种子 2/3 直接死在时间 0：

```
# ** Warning: (vsim-7084) No solutions exist which satisfy the specified constraints; randomize() failed.
# ** Fatal: [RNDFAIL] channel packet randomization failure!   (mcdt_pkg.sv:138)
```

原因是 `chnl_trans` 里有一条**硬约束** `pkt_nidles inside {[1:10]}`：test 层把
`pkt_nidles` 随机成 11 或 12 时，`send_trans()` 里的 `pkt_nidles == local::pkt_nidles`
就和硬约束冲突，求解器报"No solutions exist"。改成 `{[6:10]}` 后所有种子都干净通过。
教训是：**test 层改约束之前，先看事务里哪些是硬约束、哪些是 `soft`**——`soft`
可以被覆盖，硬约束不行，只能让 test 的取值范围落在硬约束的子集里。

顺带还把回归流程加固了一下：`make reg` 每跑完一个用例就检查该次的 log
里有没有 `Errors: 0`，没有就打印 `*** <test> FAILED` 并立刻以非 0 退出码中止：

```makefile
$(RUN_BASE) -l run_$${t}_$${s}.log ... -do "coverage save -onexit ...; run -all; quit -f" || exit 1; \
grep -q "Errors: 0" run_$${t}_$${s}.log || { echo "*** $$t seed $$s FAILED"; exit 1; }; \
```

这一步是必要的：`vsim -do "...; quit -f"` 里的 `quit -f` 会把退出码强制成 0，
所以 `$fatal` 之后 make 完全感知不到，回归会带着一条"其实挂了"的用例继续跑完，
最后合并覆盖率时把脏数据也算进去（我这次就踩到了：`single_test` 的种子 2/3
其实死在时间 0，合并报告的断言覆盖率因此莫名少了 1 条，从 100% 掉到 94.11%）。

### 2.5 剩下那几项为什么覆盖不到

**（a）`all_fifo_full`（三个通道的 FIFO 同时满）——被"停止策略"和"仲裁行为"夹住了。**

两个原因叠加，导致这 21 次回归里一次都没采到：

1. `fifo_full_test` 的停止条件是"至少 2 个通道 `ready==0`"，一旦满足就立刻掐断
   三条 generator 线程。所以在第三个通道把 FIFO 写满之前，激励已经停了——
   实测停止那一刻的 `ready flags = 'b100`（ch0、ch1 满，ch2 还在写）。
2. 就算不掐断，也很难踩到：FIFO 非空就 `slvx_req_o=1`，arbiter 每拍必然从
   "正在被服务的那一个"里读走 1 个数据，被服务通道的 margin 在同一拍就往回涨；
   而第三个通道要写满，得靠"仲裁一直停在别的通道上"这一段时间。所以"三个 margin
   同时为 0"只可能出现在某一拍的边界上，是个极窄的采样竞争窗口。

功能清单里 `f0full_f1full`、`f0full_f2full`、`f1full_f2full` 三个"两两同时满"的
bin 都命中了，说明"FIFO 满 → ready 拉低 → 反压"这条链路验证到位，缺的只是
"三个同时满"这个瞬间。要强行凑到它，得专门造一个"三通道同时长突发、
且仲裁从不在中间切换"的场景，收益远小于代价。

**（b）`validXid` 里的 `valid_single` / `same_id_single` / `diff_id_single`——覆盖率模型写法本身的问题。**

这三个 cross bin 是用 `binsof(valid.single)` 去选子集的，而 `valid.single = (0 => 1)`
是一个**转移(transition) bin**。合并报告里有两组数据摆在一起看就很清楚：

| 层级 | bin | 命中次数 |
|---|---|---|
| coverpoint `valid` | `burst` = (1=>1) | 41729 |
| coverpoint `valid` | `single` = (0=>1) | 3347 |
| cross `validXid` | `valid_burst` = binsof(valid.burst) | 41729 |
| cross `validXid` | `valid_single` = binsof(valid.single) | **0** |

`(0=>1)` 这类"起点值 ≠ 终点值"的转移 bin 在 cross 里被统计成 0，而 `(1=>1)`
这种自发自收的转移 bin 却能正常进 cross。功能上并没有漏——父 coverpoint
`valid.single` 实打实命中了 3347 次，说明"输出侧从空闲到开始搬数据"这个场景
激励已经造出来了（`single_test` 的 6~10 拍包间空隙就是为它准备的）。这属于
Questa 对跨拍转移 bin 参与 cross 时的统计口径问题，加再多激励也改不动；
要不要把这 3 个 bin 从覆盖率模型里改写成 `binsof(valid) intersect {1}`
这种值域写法，是覆盖率模型维护的事，不该为了凑 100% 去改 DUT 或硬造激励。

**（c）`arbiter.v` 第 72 行的 `default : n_state = IDLE;`——不可达的防御代码。**
`c_state` 的取值只可能是 `IDLE/GRANT0/GRANT1/GRANT2` 四种，`case` 的 `default`
分支是写给人看的防跑飞代码，激励再怎么造也进不去。这就是 arbiter
branch 96.77%、statement 97.43% 的那 1 个缺口。

**（d）`rstn_i` 的 1→0（toggle）——复位只发生一次。**
TB 只在开头打了一次复位，`rstn` 没有第二次下降沿，所以每个实例都固定缺这 1 个 bin。
这是 TB 结构决定的，不是覆盖率漏洞。

## 3 Lab3：把 mailbox 换成 analysis port / analysis FIFO

### 3.1 改了哪四处

| 组件 | 改前 | 改后 |
|------|------|------|
| `chnl_monitor` | `mailbox #(mon_data_t) mon_mb;` + `mon_mb.put(m)` | `uvm_analysis_port #(mon_data_t) mon_ana_port;`（构造函数里 `new("mon_ana_port", this)`）+ `mon_ana_port.write(m)` |
| `mcdt_monitor` | 同上 | 同上 |
| `mcdt_checker` | `mailbox #(mon_data_t) in_mbs[3] / out_mb`，用 `get()` 阻塞取 | `uvm_tlm_analysis_fifo #(mon_data_t) in_tlm_fifos[3] / out_tlm_fifo`，同样用 `get()` 取 |
| `mcdt_env.connect_phase` | 把 checker 的 mailbox 句柄赋给 monitor（`mon.mon_mb = chker.in_mbs[i]`） | `monitor.mon_ana_port.connect(chker.in_tlm_fifos[i].analysis_export)` |

### 3.2 为什么这么换

- mailbox 是**点对点**的：monitor 必须知道 checker 的 mailbox 句柄，等于 monitor
  反向依赖了 checker，环境一改（比如再加一个 reference model 也要同一份数据）就得
  回来改 monitor；而且 `put()` 可能阻塞，monitor 会被下游拖慢。
- analysis port 是**广播**的：monitor 只管 `write()`，一个 port 可以 `connect`
  到任意多个 analysis FIFO/export，monitor 不认识下游，也不会被阻塞。
- `uvm_tlm_analysis_fifo` 是“带 `analysis_export` 的无限深 FIFO”，所以 checker 侧
  的代码几乎不用动——还是 `get()`，只是取的对象从 mailbox 变成 FIFO。

### 3.3 改造后的环境结构

```
uvm_test_top  (mcdt_basic_test)
├── env  (mcdt_env)
│   ├── agents[3]  (chnl_agent)
│   │   ├── driver  (chnl_driver)     ← seq_item_port.get_next_item()/item_done()
│   │   ├── monitor (chnl_monitor)    → mon_ana_port ──────┐
│   │   └── sqr     (chnl_sequencer)                       │
│   ├── mcdt_mon    (mcdt_monitor)    → mon_ana_port ──────┤
│   ├── chker       (mcdt_checker)    ← in_tlm_fifos[3] ←──┤
│   │                                 ← out_tlm_fifo    ←──┘
│   └── cvrg        (mcdt_coverage)   ← 直接采样 chnl_vifs/mcdt_vif 的 XMR
└── virt_sqr  (mcdt_virtual_sequencer)  chnl_sqrs[3] + mcdt_vif
```

TLM 连接只有 `connect_phase` 里的四行（三路输入 + 一路输出）：

```systemverilog
foreach(agents[i])
  agents[i].monitor.mon_ana_port.connect(chker.in_tlm_fifos[i].analysis_export);
mcdt_mon.mon_ana_port.connect(chker.out_tlm_fifo.analysis_export);
```

改成 TLM 之后有两点“看不见”的收益：一是 monitor 里不再有 `put()`，采样线程
不会被下游阻塞，采样时刻与 DUT 时钟严格对齐；二是 `connect_phase` 成了唯一的
“连线清单”，看这一个函数就知道谁给谁供数据，而 mailbox 版本里连线是散落在
`new()` 里 `new()` 出来的。

### 3.4 顺手修掉的一个坑

`mcdt_root_test::end_of_elaboration_phase()` 里原本写的是
`uvm_root::get().set_timeout(10ms)`。UVM 内部是拿**仿真精度单位**的 `$time`
去和这个值比的，而 tb 的 timescale 是 `1ns/1ps`，于是 10ms 被当成 10µs——
basic_test 跑到 37µs 才结束，结果在 10µs 就被 `PH_TIMEOUT` 强杀了。改成
`set_timeout(10s)`（数值上等价于 10ms 的仿真时间）之后就是干净的正常结束。

### 3.5 结果

`+UVM_TESTNAME=mcdt_basic_test`：

```
# [CMPSUCD]  3659 条（grep -c 统计）
# UVM_ERROR :    0
# UVM_FATAL :    0
# Errors: 0, Warnings: 1
```

3659 次比对全过，0 error。比 Lab2 的 3660 少 1 条，是因为 basic 用例结尾还是
`#10us` 的固定等待（Lab4 才改成等 FIFO 排空），最后一个数据可能还在 arbiter
到输出口的路上。TLM 改造没有改变任何功能结果，`[CMPFAIL]` 一条都没有。

### 4.1 剥离的对应关系

|---|---|
| `mcdt_basic_test` | `mcdt_basic_virtual_sequence`（原有，仅把结尾的 `#10us` 改成等排空） |

每个 test 只剩三行：

```systemverilog
task run_top_virtual_sequence();
  mcdt_burst_virtual_sequence top_seq = new();
  top_seq.start(env.virt_sqr);        // 挂在virtual sequencer上跑
endtask
```

### 4.2 并行控制怎么拆到两个类里

原来 test 层是“一个 `do_config()` 把所有 generator 的 `ntrans/data_size/nidles`
都 `randomize with` 掉，再在 `run_phase` 里 fork 三个 `gen.start()`”。拆开之后：

- **要发什么**（`ntrans`/`data_size`/`ch_id`/`nidles`）下移到 `chnl_data_sequence`
  的 rand 成员 + `uvm_do_on_with` 的约束里，随机化和“产生激励”的责任归 sequence；
- **什么时候发、并在哪个 sequencer 上发**由 virtual sequence 的 `fork ... join` 决定，
  `p_sequencer.chnl_sqrs[i]` 负责把每条 sequence 路由到对应通道的 sequencer；
- sequencer 只做“仲裁 + 转发”：driver 通过 `seq_item_port.get_next_item(req)` 拿到 item，
  驱动完 `seq_item_port.item_done(rsp)` 把 response 送回 sequence 的 `get_response()`。
  这就是把原来的 `req_mb.put/get` 双向握手换成了 UVM 的 item/response 机制。

### 4.3 fifo_full 的“条件停止”怎么在 sequence 里做

原来 SV 环境是靠 `-> gen_stop_e` + `disable gen_threads` 强杀 generator 线程。
到了 UVM，sequence 挂在 sequencer 上，用 `disable fork` 强杀很容易把 sequencer 的
仲裁锁搞脏。所以换成一个**优雅停止**：

```systemverilog
// package作用域的一个标志位
bit chnl_seq_stop = 0;

// chnl_data_sequence::body() 每发一个包前检查一次
repeat(ntrans) begin
  if(chnl_seq_stop) break;
  send_trans();
end
```

virtual sequence 里则是“三条 data sequence + 一个监控线程”并发：

```systemverilog
fork
  `uvm_do_on_with(chnl_data_seq, p_sequencer.chnl_sqrs[0], {ntrans inside {[1000:2000]}; ...})
  ...(1)、(2)
  begin
    this.wait_two_chnl_fifo_full();   // 等到 countones(ch_ready) <= 1
    chnl_seq_stop = 1;                // 叫停：三条sequence发完当前包就退出
  end
join
this.wait_all_fifo_drain();           // 再等三个margin都回到32 + 5拍(dut打拍输出)
```

`mcdt_virtual_sequencer` 里除了 `mcdt_vif` 还挂了三个 `chnl_intf`，因为“FIFO 满不满”
要看 `ch_ready`/`ch_margin` 这类状态信号，光有 `mcdt_intf` 观察不到。

### 4.5 实验4开头那几道回顾题的答案

**（1）环境里有几种 `uvm_component`？**

这份代码一共用到 8 种：`uvm_test`（`mcdt_root_test`）、`uvm_env`（`mcdt_env`）、
`uvm_agent`（`chnl_agent`）、`uvm_driver`（`chnl_driver`）、`uvm_sequencer`
（`chnl_sequencer` / `mcdt_virtual_sequencer`）、`uvm_monitor`（两个 monitor）、
`uvm_scoreboard`（`mcdt_checker`）、以及最朴素的 `uvm_component`（`mcdt_coverage`，
因为它不需要 driver/monitor 那些端口，只是挂个采样线程）。
`chnl_trans` 和各类 sequence 是 `uvm_object` 派生，不是 component。

**（2）出现了哪些 phase？**

只有 4 个，而且分工很像 SV 环境的三个动作：

| phase | 对应 SV 环境的哪一步 | 本环境里干什么 |
|---|---|---|
| `build_phase`（自顶向下） | `new()` + 例化子组件 | 建 agent/monitor/checker，`uvm_config_db::get` 取 vif |
| `connect_phase`（自底向上） | 手写句柄赋值 | monitor 的 analysis port 连到 checker 的 analysis FIFO；driver 的 `seq_item_port` 连 sequencer 的 `seq_item_export` |
| `end_of_elaboration_phase` | 环境搭完后的最后检查 | 设置 UVM 超时兜底 |
| `run_phase` | `initial` 里的 fork-join | 采样、比对、发激励 |

顺序上 `build` 是自顶向下、`connect` 是自底向上，所以 `connect_phase` 里拿到的
子组件句柄一定是已经 `new` 过的——这就是为什么"连线"能集中写在一个函数里。

**（3）interface 指针怎么从 TB 传到组件里？**

TB 的 `initial` 里往 `uvm_config_db` 里 `set`，组件在 `build_phase` 里 `get`：

```systemverilog
// tb.sv
uvm_config_db#(virtual chnl_intf)::set(uvm_root::get(), "uvm_test_top.env.agents[0]", "vif", chnl0_if);
// chnl_agent::build_phase
if(!uvm_config_db#(virtual chnl_intf)::get(this, "", "vif", vif))
  `uvm_fatal("GETVIF", "cannot get vif handle from config DB")
```

关键是 `set` 的第三个参数是**路径字符串**，`get` 的第一个参数是 `this`：
`get` 会把 `this` 的全名和 `set` 的路径拼起来做匹配，所以路径写错（比如
`agents[0]` 少了个 `s`）就会 `get` 到 null，然后 fatal。

**（4）和 SV 环境的相同点/不同点？**

相同的是"三段式"骨架：建环境 → 连环境 → 跑环境，连线的拓扑也没变
（monitor → checker，sequence → driver）。
不同的是：SV 里这些全靠 `new()` 和手工赋值，谁先谁后由代码顺序决定；
UVM 把它拆成了有先后约束的 phase，并且把"连线"变成显式的 `connect()` 调用
（`connect_phase` 里漏连一根线，编译不报错、仿真跑起来照样没有数据，
所以 `connect_phase` 一定要写 `check_phase`/自检或者至少看波形确认）。

**（5）TLM 端口 vs mailbox？**

mailbox 是**点对点 + 有容量**的：`put()` 在 mailbox 满时（容量默认为 0 表示无限，
但 `new(n)` 指定容量后就会阻塞）会阻塞生产者，monitor 会被下游拖慢；而且
两个组件必须先互相认识（拿到对方的 mailbox 句柄）。
analysis port 是**广播 + 不阻塞**的：`write()` 立刻返回，一个 port 可以连任意多个
`analysis_export`，monitor 完全不知道下游是谁。代价是 analysis FIFO 没有上限，
高速采样会比慢速消费积压内存——这是用"耦合度"换"内存"的典型取舍。
