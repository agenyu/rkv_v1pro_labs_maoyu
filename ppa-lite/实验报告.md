## 1 工程概述

PPA-Lite 是一个挂 APB 3.0 从接口的小型数据包处理加速器。软件通过 APB 把一帧
数据写进片内 8×32 bit 的 packet SRAM，置位 start 后，处理核按包头里的长度和
类型把 payload 的累加和与异或值算出来写回结果寄存器，同时给出格式合法性、
各类错误标志和中断输出。四个实验分别对应接口、处理核、系统集成和覆盖率收敛。

### 1.1 模块划分

| 模块 | 文件 | 职责 |
|---|---|---|
| `apb_slave_if`（u_m1） | `rtl/apb_slave_if.sv` | APB 两段式从接口、CSR 读写、PKT_MEM 窗口、PSLVERR、IRQ |
| `packet_sram`（u_m2） | `rtl/packet_sram.sv` | 8×32 bit 单写双读同步 SRAM |
| `packet_proc_core`（u_m3） | `rtl/packet_proc_core.sv` | 三态 FSM、包头解析、payload 算和、错误判定 |
| `ppa_top` | `rtl/ppa_top.sv` | 三个子模块互联，对外的唯一 APB 端口 |

### 1.2 寄存器映射

| 地址 | 名称 | 属性 | 复位值 | 说明 |
|---|---|---|---|---|
| 0x000 | CTRL | RW | 0x0 | bit[0] enable，bit[1] start（自清） |
| 0x004 | CFG | RW | 0xF1 | [7:4] type_mask，[0] algo_mode |
| 0x008 | STATUS | RO | 0x0 | [0] busy，[1] done，[2] error，[3] format_ok |
| 0x00C | IRQ_EN | RW | 0x0 | [0] done_irq_en，[1] err_irq_en |
| 0x010 | IRQ_STA | RW1C | 0x0 | [0] done_irq，[1] err_irq |
| 0x014 | PKT_LEN_EXP | RW | 0x0 | 期望包长，0 表示不检查 |
| 0x018 | RES_PKT_LEN | RO | 0x0 | 解析出的包长 |
| 0x01C | RES_PKT_TYPE | RO | 0x0 | 解析出的包类型 |
| 0x020 | RES_PAYLOAD_SUM | RO | 0x0 | payload 累加和 |
| 0x024 | RES_PAYLOAD_XOR | RO | 0x0 | payload 异或值 |
| 0x028 | ERR_FLAG | RO | 0x0 | [0] 长度错，[1] 类型错，[2] 校验错 |
| 0x040–0x05C | PKT_MEM | RW | 0x0 | 8 个包数据 word，地址 [5:2] 索引 |

### 1.3 关键行为

**PSLVERR 的产生条件**（`apb_slave_if.sv` 第 110–131 行）：

1. 写 PKT_MEM 且 `busy_i=1`（处理中不允许改包）；
2. 写只读寄存器或保留地址；
3. 写 CTRL 置 start，但 `enable=0` 且当前不是刚被接受的 start 脉冲；
4. 读保留地址。

**PSLVERR 与 PREADY 的采样点**：`access = PSEL && PENABLE`。
`PREADY` 恒为 1（零等待态），所以一个 APB 传输固定两拍：SETUP 拍
`PSEL=1, PENABLE=0`，ACCESS 拍 `PENABLE=1`，错误在 ACCESS 拍由 PSLVERR 给出。

**处理核 FSM**（`packet_proc_core.sv`）：

```
S_IDLE --start--> S_PROCESS --读完最后一字--> S_DONE --下一次 start--> S_PROCESS
```

`S_PROCESS` 里按 `words_for_len(len)` 逐字读 SRAM，第一字解析包头
（byte0 长度、byte1 类型、byte2 flags、byte3 校验和），后续字累加 sum 与 xor。
`S_DONE` 拉高 `done_o`，并在下一次 start 被接受时清除。

**中断**：`done_irq` / `err_irq` 由 `S_DONE` 阶段按错误情况置位，
经 `IRQ_EN` 使能后驱动 `irq_o = done_irq_sta_r || err_irq_sta_r`，只能通过写
`IRQ_STA` 的 RW1C 清除。


`fork...join` / `fork...join_any`（IRQ 等待与超时分支）、`semaphore`（APB 互斥）、
事件与超时保护。

### 2.3 参考模型与检查方式

`packet_item` 里独立实现了和 RTL 同语义但不同写法的期望值计算：
`payload_sum()`、`payload_xor()`、`length_error()`、`type_error()`、
`chk_error()`、`format_ok()`。每条用例在流程结束后逐项比对：
`STATUS` 四个状态位、`RES_PKT_LEN / TYPE / SUM / XOR`、`ERR_FLAG` 三位。
任何一项不符就 `check()` 计错，用例结束时 `finish()` 以 `$fatal` 退出，
日志不会出现 `[TEST PASS]`，回归立刻判失败。

### 5.3 覆盖率是怎么提上来的

上一版（13 个用例、39 次仿真）的数据是：语句 96.93%、分支 95.14%、
条件 96.42%、FSM 100%、翻转 92.60%，总计 96.48%。
这次做了三件事把空洞收掉，改动全部有据可查：

**（1）新增定向用例 `lab4_code_cov_test`。** 分析 `cov/dut_merged.txt` 的
`***0***` 条目后发现，空缺并不是"激励不够随机"，而是三类结构性死角：

- **集成后的 M1 从没被读过 CTRL / CFG / PKT_LEN_EXP。**
  Lab1 的三个用例走的是 TB 里独立例化的 `u_lab1_m1`，它不在 `/tb/dut` 的
  统计范围内；而顶层用例只读 STATUS、RES_*、ERR_FLAG。
  于是 `readable_csr()` 里三个 case 分支恒为 0。
  → 新用例在顶层把 11 个可读 CSR 全读一遍。
- **PADDR 的高 5 位和低 2 位从没翻转过。**
  顶层只访问 0x000–0x05C，PADDR[11:7] 和 PADDR[1:0] 一直是 0。
  → 新用例访问非字对齐地址 0x001/0x002/0x003 和未映射高地址
  0x080/0x100/0x200/0x400/0x800/0xFFC，这些访问按规则返回 PSLVERR，
  既是合法的负向测试，又把每个 bit 都置 1 再归零。
- **结果类型的 bit4 / bit6、exp_len 的 bit0 / bit1 从没被置过。**
  原有用例只用 0x01/0x02/0x04/0x08 四种合法类型（bit0–bit3）和
  4/8/16/32 四个包长（bit2–bit5）。
  → 新用例加非法类型 0x10、0x40（正好点亮 bit4、bit6），
  以及 exp_len = 5 / 6 / 7 / 32 / 16 / 8 的边界序列，
  让 `exp_len_r[0]`、`[1]`、`[4]`、`[5]` 都能双向翻转。

**（2）`packet_sram` 的循环变量改为块内 automatic 声明。**
原来 `integer i;` 声明在模块级，覆盖工具把它当成一个 32 位硬件节点，
`i[0-31]` 全不翻转，一次性吃掉 64 个 toggle bin（分母里 278 个 bin 有 64 个是它）。
它只是复位循环的计数器，综合时会被完全展开、不产生任何硬件。
改成 `for (int i = 0; ...)` 收进 `always_ff` 块内后，该节点不再出现在覆盖率里。
这是唯一一处 DUT 源码改动，不改变任何功能行为（`packet_sram` 的
statement / branch 覆盖率在改动前后都是 100%）。

**（3）其余 13 个用例、`tb`/`Makefile` 的检查逻辑没有放松。**
没有删除用例、没有加 `coverage exclude`、没有改功能 bin 的定义来凑数。

### 5.4 剩余未覆盖项与解释

原始库剩余未命中一共 13 个 bin，全部属于"设计上不可达"或"防御性代码"：

| 对象 | 未命中 | 数量 | 原因 |
|---|---|---:|---|
| `packet_proc_core` FSM `default` 分支及其 5 条赋值语句 | 不在 S_IDLE/S_PROCESS/S_DONE 之内 | 2 branch + 5 statement | 状态是 2 bit 编码 3 个值，`2'b11` 只能由非法跳变产生，正常复位与运行都到不了。这段是防御性写法，保留是为了防止 SEU 或仿真期 X 态导致锁死 |
| `packet_proc_core` 条件覆盖 Row 4 | `busy_r && start_i` 同时为真 | 1 condition | 处理中收到 start 会被 `!busy_r` 挡在门外，这个组合在协议上不允许出现，属于互斥保护本身 |
| `packet_proc_core` 148 行 `if/else-if` 的 all-false 分支 | `issue_read_r` 与 `wait_read_r` 同时为 0 | 1 branch | 进入 S_PROCESS 时 `issue_read_r` 必为 1，之后两者交替为 1，全 0 组合不可达 |
| `apb_slave_if.PREADY` | 1→0 翻转 | 2 bin | APB 零等待实现，`assign PREADY = 1'b1`，永远不会拉低 |
| `ppa_top.PREADY`（端口） | 1→0 翻转 | 2 bin | 同上，顶层端口直接透传 |

这五项都不是"激励不够"，加再多随机包也走不到；要强行命中只能改 DUT
（比如给 FSM 加故障注入、把 PREADY 改成可配），那属于改设计而不是验证，
所以如实记录、不伪造。

处理方式是**登记 + 过滤**，而不是改 RTL：

1. `coverage_filter_register.xlsx` / `.csv` 逐条登记（对象、位置、bin 数、
   原因、结论、对应的 exclude 配置行），共 8 行。
2. `cov_exclude.do` 用 `coverage exclude` 把这些 bin 从分母里排除，
   每条注释都标了对应的 CSV 行号。
3. `make filtercov` 生成 `cov/dut_filtered.ucdb`，`make report` 从过滤库出报告。

过滤后五类覆盖率全部 100.00%；原始库 `cov/dut_merged.ucdb` 仍然保留，
两组数字都能现场拿出来对照。

功能覆盖率 100%，说明**所有定义的功能场景都被打到了**；
代码层面的这 13 个 bin 属于结构性不可达，不影响功能完备性结论。

### 6.9 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `sqlite3_open ... _lib.qdb` | 工程在中文路径 | 挪到纯英文路径 |
| 编译一直报同样的错但 `comp` 很顺 | `work/` 是上次失败留下的空壳，`comp` 跳过了 `vlib` | 删 `work/` 重编 |
| 换路径后 vsim 报莫名 error | 编译库从旧路径带过来，含过期编译单元 | 删 `work/` 重编 |
| make 返回 0 但用例挂了 | `quit -f` 会强制退出码为 0 | 以日志 `[TEST PASS]` 与 `Errors: 0` 为准 |
